# Releasing

Two artefacts go out together and must stay a matching pair: the `dratify`
package on [PyPI](https://pypi.org/project/dratify/) and the `dratify` crate on
[crates.io](https://crates.io/crates/dratify). They are two implementations of
the same rules, and the claim this package makes is that they agree. A release
where they are different versions makes that claim uncheckable.

Publishing is automated. Pushing a `v*` tag runs
[`.github/workflows/release.yml`](../.github/workflows/release.yml), which:

1. runs the suite **on the tagged commit** and fails if the tag does not name
   the version being built;
2. publishes the sdist and wheel to PyPI;
3. checks whether the crate version is already on crates.io, and publishes it
   if not.

Both registries use **Trusted Publishing** over GitHub OIDC, through the `pypi`
and `crates` environments. There is no token anywhere and nothing to rotate.

crates.io required one manual `cargo publish` before Trusted Publishing could
be configured. That is done; it is not needed again.

## 1. The tree has to be honest

```bash
make gate                     # tests, coverage, cargo test, clippy
make native && make test-native   # the suite with a native checker present
python bench/repro.py --quick     # the numbers the README quotes
```

Then the part that is not a command: **read the claims**. Every quantitative
statement in `README.md`, `SECURITY.md` and `AGENTS.md` must either be
regenerated by `bench/repro.py` or be something a test asserts. This has gone
wrong before — the README carried a speed table computed from CNF files that
were not in the repository, and an agreement result against `drat-trim` that
nothing reproduced, through three releases.

At minimum check:

- the test count and the coverage **floor** (not the snapshot percentage)
- the speed table and the Rust-vs-Python range, from `bench/results.json`
- the perturbation counts in the "What skip work means" section
- anything in "Honest limitations" that is no longer a limitation

## 2. Version

Three files state it, and `tests/test_packaging.py` fails if they drift:

```bash
$EDITOR pyproject.toml rust/Cargo.toml src/dratify/__init__.py
(cd rust && cargo update -p dratify)   # keep Cargo.lock in step
make test
```

## 3. Changelog

Move `[Unreleased]` to the new version with today's date, and add the
comparison link at the bottom. Write for someone deciding whether to upgrade.

## 4. Tag

```bash
git tag -s v0.1.4 -m "dratify 0.1.4"
git push origin main --follow-tags
```

The tag push is what publishes. Watch it:

```bash
gh run watch $(gh run list -w release -L1 --json databaseId -q '.[0].databaseId')
```

If the `build` job fails on the version check, the tag names a version the tree
does not declare. Delete the tag, fix the version, tag again — do not re-run
the job. The PyPI step sets `skip-existing`, so a re-run of the *same* release
is safe, and a forgotten version bump would otherwise publish nothing while
reporting success. That is what the version check is for.

## 5. Downstream

`cdclkit` depends on this package, and its Rust half depends on this crate.
After a release, bump both there — `native/Cargo.toml` and `pyproject.toml` —
and let its `test_both_halves_require_the_same_dratify` confirm they match.

Note the ordering: dratify's own `differential` CI job installs
`cdclkit-native`, so release dratify first, then cdclkit.

## 6. After

Open `[Unreleased]` again. If anything in this file was wrong while you were
following it, fix it now rather than next time.
